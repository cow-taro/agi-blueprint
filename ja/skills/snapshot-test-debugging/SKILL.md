# テストの実行と失敗解析（snapshot-test-debugging）

テスト実行・サーバー起動・DB リセット・golden の記録に触れる作業では、**着手前に必ず**この手順を確認してから動く。ここに無い独自コマンド・独自検証スクリプトを発明しない（実名は SETUP-CHECKLIST A5 で確定したものを使う）。

必読: `templates/test-runbook-template.md` を複製したテスト実行手順書（runbook）。確定コマンドは runbook を正とし、runbook が古ければ先に直してから実行する。

## 0. コマンド出力を握りつぶさない（絶対）

- **`2>/dev/null` / `>/dev/null` / `| tail` / `| head` / `| grep` で結果を切り捨てる実行をしない。**
- テスト・DB リセット・DB 操作などの **stdout/stderr は全部出す**。長い場合はツールが書く端末ファイルやログファイルを読む。パイプで間引かない。
- 「進捗がわからない」「フリーズに見える」状態を自分で作らない。出力を消して状況を隠す実行方法は使わない。
- 本当に多すぎて人間の閲覧だけ困るときだけ、ユーザー指示のうえで減らす。AI 側は出力増を理由に抑制しない。

## 1. 実装前: 影響範囲の既存テストを実行して緑を確認する

ソースを 1 行も変える前に、影響範囲の**既存**テストを実際に実行して全件緑を確認する。正本は `rules/03-test-before-implementation.md` の「1. 実装前ゲート」。

## 2. 実行前に必ずやること

### 残留プロセスの確認

テスト用サーバーや前回起動したプロセスが、前回の異常終了で残留していないか、テストの**たびに**確認する。

```bash
ps aux | grep <server-process-name> | grep -v grep
```

- 想定通り（自分が今起動した分だけ）なら問題なし。
- 見覚えのない古い起動時刻のプロセスが残っていたら、**内容を確認してからでないと自動 kill しない**。無関係なプロセスを誤って殺さないため。

### 実行権限は引数に実際に入れる（送信前点検・絶対）

サンドボックス環境では、ループバック接続・ポート調査・`sudo` を伴うコマンド等、**権限の付与が必要なコマンド**がある。

- 権限が必要なコマンドは、**ツール呼び出しの引数（引数 JSON の最上位フィールド）に権限フィールドを実際に入れて**実行する。コマンド文字列や発話の中ではない。
- **「入れた」と発話していても、実際の引数から抜けていることがある。** 送信前に、いま組み立てた引数を読み返し、権限フィールドが実際に入っていることを確認してから実行する。確認しないままの再送をしない。
- 権限が無いと、シェルコマンドが**別のネットワーク名前空間で動く**など、外側の実態が「見えない」状態になり、誤判定のうえ無警告で進むことがある。この状態の実行結果は信用できない。
- **失敗したときの診断順**: 権限まわりのエラー（`sudo` の `no new privileges` 等）やローカル接続失敗が出たら、**環境を疑う前に自分の引数を実物で確認する**。権限フィールドが抜けていたら、同じコマンドを権限付きで 1 回だけ再実行する。
- **数分前に同じコマンドが成功しているのに失敗するとき、原因は環境ではなく自分の実行形態（引数からの権限フィールド漏れ）であることが多い。** 権限なしのまま長時間の全件テストを回し、全件エラーの無駄な実行と費用を繰り返さない。

### DB リセット方式の分岐（物理スナップあり／なし）

判定は設定（`skills/fast-snapshot-db-reset/SKILL.md` の導入状態。既定は論理ロード）。**物理スナップを入れていない開発機もある。未導入なら従来どおりの論理ロードでよい。**

| 環境 | 全件・リセット付き実行 |
|---|---|
| 物理スナップ導入済み | dump／seed／スキーマ変更後は先にスナップを取り直してから**常に物理スナップで実行**。スナップが古いことを理由に論理ロードへ逃げない |
| 未導入 | 従来どおり論理ロード（ダンプ＋seed）。スナップ取得は不要 |

- 導入済みマシンでの禁止: 「スナップが古い」から論理ロードで全件を回すこと。論理ロードを毎回やらないためにスナップを置いている。
- 物理スナップは seed を再適用しない（スナップに込み）。古いスナップなら取り直す。
- 論理ロードに戻してよい例外: 物理スナップ復元の失敗後の復旧（`skills/fast-snapshot-db-reset/SKILL.md` の「6-1. 失敗時の復旧（論理リセット）」）。

### リセットで再現されない変更を適用したままテストするとき

DB リセットは「ダンプ復元 ＋ seed 適用」で行われる。この過程で**再現されない変更**（マイグレーションで追加したインデックス、seed に含めていないフィクスチャ、手動投入データなど）を適用した状態でテストすると、**リセットでその変更が消える**。

- そうした変更を適用した状態で計測・検証するときは、必ずリセットをスキップする方式（環境変数等、A5 で確定したもの）で実行する。インデックス性能比較の手順例: (1) インデックスなしで計測 → (2) マイグレーション適用 → (3) リセットせずに計測。

### 性能比較のベースラインが分からないときは両方測り直す

どのログが「本来の初期状態」か確信が持てない場合、推測で 1 つのログをベースラインと決めつけない。**条件（例: インデックスあり／なし）を両方その場で実測し直す。** 過去ログの解釈に頭を使うより測り直す方が速く確実。

## 3. 想定外のときは「証拠を調査してから」判断する

テストが動かない・出力が出ない・異常に遅い等の想定外が起きたとき、以下を厳守する。

- **原因を推測で決めつけない。**「たぶんコードのせい」「たぶん運用のせい」といった当てずっぽうで動かない。まず具体的な証拠（実際のエラーメッセージ、サーバー実ログ、コマンドの実出力、実行したコマンドそのもの）を調査する。
- **関係のありそうなファイルを手当たり次第に開いて原因と決めつけない。** 証拠が指し示す箇所だけを調べる。編集していないファイルを疑う場合も、まず「そのファイルが本当に関与している」証拠を出す。
- 証拠が揃うまで修正に着手しない。証拠が示す事実だけに基づいて対応する。

## 4. 既存バグがあるコードに golden を作るとき

### ステップ A: 現状のバグ挙動ごと golden として記録する

バグを修正してから記録するのではなく、**現在の（バグを含む）挙動を golden として記録する**。これにより、修正後に「レスポンスが変わった」ことをテストが検出できるようになる。

### ステップ B: 実装前に「失敗予測」を文書化する（必須）

テストを記録したら、ソースコードを 1 行も変更する前に、対象の plan md に明記する（記入式ひな形は `templates/desired-red-gate-checklist.md`）。

1. **必ず失敗するテスト（変化が期待される）**: テスト名・現在の挙動（バグ状態）・修正後の期待挙動
2. **変化しないはずのテスト**: 同じ関数を呼ぶ他のエンドポイント・他のパラメータパターン。「なぜ変化しないか」の論拠も記載
3. **実装方式による条件分岐がある場合**: 「方式 A なら何が変わり、方式 B なら何が変わる」を事前に整理

### ステップ C: 実装後の確認

- 予測した「必ず失敗するテスト」だけが失敗していること
- 「変化しないはず」のテストが全件パスしていること
- 上記を満たしたうえで、失敗したテストのみ再記録する
- 予測と違う失敗が出た場合は**直ちに修正を止め**、ユーザーに差異を報告して指示を仰ぐ

## 5. 失敗解析の手順（最重要）

### テストフレームワークのデバッグダンプに惑わされない

多くのテストフレームワークは失敗時、実際のエラーより**先に**大量のデバッグダンプ（変数・レスポンス全フィールドの列挙等）を出力する。**これは失敗の原因ではない。** 実際の原因は出力の**最後**のエラーセクション（`Errors:`、`TestFailError`、ステータスコード不一致、Python トレースバック等）にある。失敗を解析するときは、まずエラーセクションを探すこと。大量のダンプ出力に時間を使わない。

```bash
grep -A 30 "^Errors:" <出力ファイル>
```

### テストのログではなく、サーバー側の実ログを見る

- テスト自体のログには、テスト実行結果とフレームワークの失敗メッセージしかない。
- **アプリケーション側の実ログ**には、個別クエリの実行時間や、サーバー内部で発生した例外の実トレースバックが出力される。性能検証（「本当に速くなったか」）も、原因調査（「なぜ 500 エラーになったか」）も、こちらのログを見て判断する。

### 根拠のない当てずっぽうの修正を禁止

- 「一般的にありがちな原因」「よくあるベストプラクティス」を、今回の具体的なエラー内容を確認せずに当てはめて修正することを禁止する。
- 修正する前に、今回発生した**具体的な**エラーメッセージ・トレースバック・ログを根拠に、このコードベース上で実際の原因を特定する。
- 原因が特定できない・複数の可能性が考えられる場合は、ログの追加確認や再現実験で絞り込んでから修正する。特定できないまま修正を試みない。

### 1 回の修正につき検証は 1 回

- 複数の修正を積み重ねてからまとめて検証しない。1 つ変更したら、その変更だけを検証する。
- 想定した結果（速度改善・テスト PASS）が得られなかった場合、**次の修正を自己判断で試みず**、実際に得られたエラー内容・ログをそのまま提示してユーザーに指示を仰ぐ。
- 性能検証では、テストの PASS/FAIL だけでなく実際の所要時間を比較する。残留プロセス等、テストが意図せず別のコード・別の環境に対して実行されていないかを都度疑うこと。
