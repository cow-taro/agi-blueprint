# クエリチューニング方針: 巨大 JOIN の分割

## 基本方針

**1 本の巨大な JOIN クエリで全部解決しようとしない。** 重いクエリを見つけたら、まずそのクエリが何をやっているかを解析し、意味のある単位（テーブル・条件）で複数の小さいクエリに分割し、アプリケーション側で結合する。

理由:

1. **小さいクエリはインデックスが効く。** 巨大な JOIN は中間結果が肥大化し、インデックスが活かせなくなる。分割すれば各クエリが素直にインデックスを使える。
2. **重い部分を確実に分離できる。** 分割すると「どのクエリだけ遅い」が特定でき、そのクエリ専用のインデックス追加や WHERE 条件の見直しといった、ピンポイントの改善がしやすくなる。
3. **段階的に絞り込める。** 前段のクエリ結果（ID リストなど）で後段のクエリを絞り込めば、後段は最初から小さいデータセットに対して実行できる。

## 重要: フィルタ条件は「JOIN の ON 句」ではなく独立クエリの「WHERE 句」にする

`UNION ALL` を含むビューは、MySQL がマージできず、参照するたびに**ビュー全体を最初から計算（マテリアライズ）する**。

- ❌ 効果なし: 巨大 JOIN の中で `LEFT JOIN SummaryView SV ON t.id = SV.id` のように**JOIN 条件（ON 句）**で絞り込んでも、ビュー内部には条件がプッシュダウンされず、常に全件マテリアライズされる
- ✅ 効果あり: `SELECT * FROM SummaryView WHERE id = %(id)s` のように、**独立したクエリの直接の WHERE 句（リテラル値）**にすると、条件が UNION ALL の各ブランチまでプッシュダウンされ、劇的に速くなる（実績例: 同条件で 30 倍以上の高速化）

大きな 1 本の JOIN クエリを分割する際は、各テーブル／ビューを個別クエリとして発行し、絞り込み条件は必ずそのクエリ自身の WHERE 句に書くこと。分割後、アプリケーション側で辞書（ID をキー）に組み立てて結合する。

## 落とし穴: ビューがネストしている場合は 2 段目まで届かない

ビューが内部で別のビューを JOIN して参照している（ビューのネスト）場合、外側のビューに `WHERE` 句を書いても、条件は外側のビュー自身の UNION ALL ブランチまでは届くが、その内部で JOIN している内側のビュー側へは届かない。結果、外側のビュー単体クエリでも重いままになる。

この場合はビューを経由せず、基礎テーブルを直接クエリして必要な JOIN をアプリ側の分割クエリとして書き直す必要がある。ビュー定義を見て、内部で別のビューを参照していないか必ず確認すること。

## 着手前に他の呼び出し元を必ず確認する

チューニング対象の API・DB メソッドが、今解析しているページ以外からも呼ばれていないか、着手前に必ず確認する。

- 同じ DB メソッドが複数のエンドポイントから呼ばれ、それぞれ異なるパラメータ・フィルタの組み合わせを渡している場合がある。
- 手順: 対象 DB メソッド名で呼び出している全エンドポイントを洗い出し、各エンドポイントをフロント側で検索して、どの画面がどんなパラメータ・呼び出し方をしているか確認する。
- 対応方針: 他の呼び出し元が要求する汎用的なフィルタ機能まで巻き込んで共有メソッドを書き換えると影響範囲が広がり壊れやすい。厳重に関係するすべてのページからの全てのパラメータ組み合わせのテストを作成し、すべての条件を満たすように修正する（全く同じ処理を実装し、いかなる条件でも完全に同じレスポンスを返す）。
- テスト作成時も同様に、対象 API の全呼び出し元・全パラメータパターンを洗い出した上でテストケースを設計する。

## 作業手順

**Step 0（必須・最初に必ずやる）: インデックス確認**

クエリチューニングを始める前に、クエリが参照する全テーブルのインデックスを `SHOW INDEX FROM テーブル名` で確認する。WHERE 句・JOIN 条件・ORDER BY で使われているカラムにインデックスがなければ、まずインデックスを追加する。インデックス追加だけで解決する場合はそれが最適。ビューのバイパスや分割は、インデックスが正しく揃った状態でまだ遅い場合に行う。

```sql
SHOW INDEX FROM <table1>;
SHOW INDEX FROM <table2>;
```

- 欠損インデックスがあれば、**直接 `ALTER TABLE` を実行しない**。必ずプロジェクトのマイグレーションファイルを作成し、そのファイル経由でインデックスを追加する。場所・形式は既存ファイルを参照して合わせること。
- MySQL の実行コマンドは出力を抑制しない（`2>/dev/null` 等の禁止は `skills/snapshot-test-debugging/SKILL.md` の「0. コマンド出力を握りつぶさない（絶対）」）。

1. 重いクエリを `EXPLAIN FORMAT=TREE` で確認し、`Materialize` / `Union all materialize` が出ていないか、どの段階で行数が絞られているかを見る（読み方の詳細は `skills/mysql-performance-diagnosis/SKILL.md`）。
2. クエリが参照しているテーブル・ビューを洗い出し、ビューのネストがないか確認する。
3. 意味のある単位（テーブル/条件）で独立クエリに分割し、絞り込み条件はそのクエリ自身の WHERE 句にリテラル値として書く。
4. 分割後、各クエリを実測し（`time.time()` 等）、想定どおり速くなっているか確認する。まだ遅いクエリが残っていれば、それが「重い部分」として特定できているはずなので、そのクエリ単体に対してインデックス追加や WHERE 条件の見直しを行う。
5. アプリ側で結果を辞書化し、元のレスポンス形式（フィールド構成）を変えずに結合する。

## IN（相関サブクエリ）を JOIN（導出テーブル）に書き換える

`WHERE id IN (SELECT ...)` の形は、MySQL が外側の行ごとにサブクエリを再評価する実行計画を組み、実質的に索引が効かず全件スキャンに近い動きになることがある。

- ❌ 効果薄い: `WHERE C.id IN (SELECT id FROM Customer WHERE ownerId IN (SELECT userId FROM Account WHERE tenantId = %(tenantId)s))`
- ✅ 効果あり: `JOIN (SELECT id FROM Customer WHERE ownerId IN (...)) CAUTH ON CAUTH.id = C.id` のように**導出テーブルとして JOIN** する。導出テーブルは 1 回だけ materialize され、その後は結合キーに対して素直に索引が使える。

「許可された id の集合を先に求めてから本体に JOIN する」パターンが出てきたら、`IN` ではなく `JOIN` で書くことを優先する。

## 複数テーブルをまたぐ OR の認可条件はインデックスが効かない

別々のテーブル（LEFT JOIN 先を含む）の列を OR で束ねる条件は、単一テーブルの単一列インデックスでは効率よく評価できない（index_merge が効かず、結局テーブル全体をスキャンして Filter で評価されることが多い）。

対応: この手の OR 条件は、**テーブル単位の単純な等値条件による `UNION`**（id の集合演算）に分割する。

```sql
-- ❌ 全件スキャンになりがちな複数テーブルまたぎ OR
SELECT ... FROM Customer C
LEFT JOIN Account A ON C.ownerId = A.userId
LEFT JOIN Account A2 ON C.subOwnerId = A2.userId
WHERE C.tenantId = %(tenantId)s OR A.tenantId = %(tenantId)s OR A2.tenantId = %(tenantId)s

-- ✅ テーブル単位の UNION で索引を使う
SELECT id FROM Customer WHERE tenantId = %(tenantId)s
UNION
SELECT id FROM Customer WHERE ownerId IN (SELECT userId FROM Account WHERE tenantId = %(tenantId)s)
UNION
SELECT id FROM Customer WHERE subOwnerId IN (SELECT userId FROM Account WHERE tenantId = %(tenantId)s)
```

各 UNION ブランチは単一テーブル・単一条件になるため、それぞれの列の単純なインデックスがそのまま使える。認可条件（tenant / department / self 等のアクセス制御）を再構築するときに特に有効。

## 共有 ID に型サフィックスがある列は、型を保持したまま結合する

複数のエンティティ種別が別々のオートインクリメント ID 空間を持ちながら、**同じ数値 id が偶然重複しうる**列（`concat(id, '-', type)` のようなサフィックス付き共有 ID）を扱うときは、**サフィックス（型）を落とした生の数値 id だけで再 JOIN しない**。

- ❌ 危険: `... JOIN Customer CL ON C.customerId = CL.id`（`C.customerId` が既に型情報を失った生の数値 id）→ もし `C` が実は別エンティティ由来の id だった場合、**たまたま同じ数値 id を持つ無関係なレコード**に解決されてしまう（別組織所属の可能性もあり、認可境界を跨いだデータ露出のリスクになる）。
- ✅ 安全: `... JOIN Customer CL ON F.parentSerialRefId = concat(CL.id, '-', '0')` のように、**毎回サフィックス込みで再構成して比較**する。型が一致しない限り絶対に一致しない。

このパターンの列を見つけたら、既存コードであっても型安全な結合になっているか必ず確認する。

## 段階的アプローチ（インデックスのみ → 効果不足なら再構築）

Step 0（インデックス確認）だけで解決しない場合、いきなりクエリ全体を書き換えず、以下の順で段階的に検証する。

1. **段階 1**: 不足インデックスのマイグレーションファイルを用意する。
2. **段階 2**: クエリ構造は変えず、インデックスだけを適用した状態で実測する。`EXPLAIN FORMAT=TREE` で実際にそのインデックスが使われているか、`Table scan` が残っていないかを確認する。**インデックス追加だけで十分なら、ここで終了してよい**（クエリ再構築は不要な複雑化を避けるため、効果が実測で確認できた場合のみ行う）。
3. **段階 3**: 段階 2 でも遅い場合のみ、クエリ自体を再構築する（本スキルの各パターンを適用）。再構築後は必ず次項の検証を行う。

## 認可条件を含むクエリを再構築する場合の検証（B2B の認可境界）

マルチテナントな B2B アプリでは、クエリが返す行の集合そのものが権限境界になっている。認可条件（tenantId / departmentId / userId による WHERE・JOIN）を含むクエリを再構築するときは、通常の golden 回帰テストに加えて、**新旧クエリが返す行の id の集合を実データで直接突き合わせる**追加検証を行う。golden 回帰は少数の代表 org/department/user しかカバーしないため、実データの多数の org/department/user で新旧の集合が完全に一致するかを確認することで、テストケースが偶然カバーできていない認可条件の抜け漏れを検出できる。

手順:

1. 再構築前のクエリ（`git show <再構築コミット>^:<path>` 等で復元）と再構築後のクエリを、それぞれ「返す id の集合」だけを取り出す形で SQL に書き出す。
2. 実データに存在する複数の tenantId（件数の多いものから少ないものまで数個）・department・userId について、両方のクエリを実行し、以下をチェックする。
   ```sql
   SELECT COUNT(*) FROM new_ids WHERE refId NOT IN (SELECT refId FROM old_ids); -- 権限外露出の疑い
   SELECT COUNT(*) FROM old_ids WHERE refId NOT IN (SELECT refId FROM new_ids); -- リグレッション
   ```
3. 両方とも 0 件であることを確認してから採用する。差分が出た場合は原因が判明するまで採用しない。
4. あわせて、認可の起点になる列に重複行や異常値（同一 userId で複数の有効アカウント等）がないかも確認しておくと、偶然の一致で見逃しやすいケースを潰せる。

## INSERT/UPDATE 系への適用時の注意

書き込み系のクエリが遅いケースに遭遇した場合、読み取り系と同じ感覚で安易に複数クエリへ分割しないこと。分割すると原子性が失われ、途中で失敗した場合にデータ不整合が起きうる。書き込みを分割する場合は必ずトランザクション（`BEGIN` / `COMMIT`、あるいは ORM 側のトランザクション制御）で囲み、整合性を担保すること。
