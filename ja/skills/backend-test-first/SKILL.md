# テスト先行・一気通貫（backend-test-first）

既存の挙動を変える変更（バグ修正・セキュリティ対応・性能改善・リファクタ等）は、**下記の順以外で実装してはならない。** 終点はテスター向け確認 md まで。途中で止めない。

- ルール要約: `rules/03-test-before-implementation.md`
- git の切り方: `skills/git-repo-operations/SKILL.md`
- テスト実行・失敗解析: `skills/snapshot-test-debugging/SKILL.md`

本スキルは**順序と完了条件の正本**。コマンド実名（A5）は SETUP-CHECKLIST で確定したものを優先し、日々の実行コマンドは `templates/test-runbook-template.md` 由来のテスト実行手順書（runbook）を正とする。

---

## 固定手順（この順以外で実装禁止）

### 0. 作業計画

- plan md（SETUP-CHECKLIST A4 のディレクトリ）に影響範囲・既存テスト・失敗予測・シード要否を書く
- 編集計画を出し、ユーザーの明示承認後にのみファイル変更（`skills/edit-plan-approval/SKILL.md`。依頼語だけでは編集しない）

### 1. ベース最新化

```bash
git fetch origin
git checkout <ベースブランチ>
git pull origin <ベースブランチ>
```

ベース SHA を plan md に記録する。

### 2. 開発ブランチ作成

```bash
git checkout -b feature/<ticket>-<short-name>
```

- **トラッキングなし**（`git checkout -b feature/... origin/保護ブランチ` は禁止）
- 保護ブランチへ直接 push しない。残置ブランチも使わない・push しない（`skills/git-repo-operations/SKILL.md`）

### 3. フィクスチャが必要な場合（実装コードより先・別検証）

- シード／スキーマ補完だけ入れる（本番ロジックはまだ変えない）
- **テストを実行して全件緑**にする（`skills/snapshot-test-debugging/SKILL.md` の「DB リセット方式の分岐（物理スナップあり／なし）」に従う）
- 赤 → 原因調査。フィクスチャ起因で問題ない差分なら golden 再記録 → 再実行で緑。予測外なら止まる
- フィクスチャ作業とロジック実装を同一ステップにしない

### 4. 実装前テスト（必須ゲート）

- 影響範囲の**既存**テスト／関連スイートを実行し全件緑
- 「前は緑だったはず」「他タスクで通っていた」は確認にならない。コマンド・件数・pass/fail を plan に書く
- 影響範囲は、変更する関数・API・シード・マーカーに紐づく**既存スイート全部**。新規 desired だけの実行では足りない
- 1 件でも赤なら実装に進まない。失敗ログを残し、`git log` / `git blame` で原因を特定して報告する（本タスク修正と混ぜない）

### 5. 不足 golden の全生成とテスト（条件付き）

**必須（既存処理の変更）**: クエリチューニング、ハンドラ／CRUD SQL の書き換え、レスポンス形状を変えうる変更など、**既存の処理結果にデグレが起きうる**とき。影響対象にケースが無い／足りない → ケース生成・記録の手順（A5 で確定したもの）で**足りない分を全て**作る。現挙動（バグ含む）をそのまま記録する。人が golden を手編集しない。生成後、そのスイートを実行して緑であること。

**スキップ可（確認クエリ追加のみ等）**: 既存ハンドラ・既存 SQL・レスポンス組み立てを触らず、認可ガード用の別 SELECT を足すだけのように、正規操作の応答デグレがまず起きない変更。このとき影響範囲の全パターン golden 新規生成は省略してよい。

- スキップするときは plan md に**スキップの理由**（何を触らないか）を明記する。黙って飛ばさない
- スキップしても「4. 実装前テスト」「6. desired red」「8. 実装後」「9. テスター用」は省略不可
- 既存の golden がある対象を触る／壊しうるなら、スキップ対象外（4 でそのスイートを回す）

### 6. desired テスト → 実装前 red

- 失敗予測を plan に書いたうえで、期待挙動のテストを追加し、**実装前に必ず失敗（red）させる**
- 失敗理由が失敗予測と一致するまで実装しない。不一致なら報告して停止
- desired だけ回して既存スイートを省略しない

### 7. 実装

- 承認済み編集計画の範囲のみ
- 設計とフローの適切さを変更範囲の小ささより優先する。ついで修正禁止

### 8. 実装後の緑と回帰

- desired が緑
- golden は**予測どおり変化したものだけ**再記録。それ以外は不変
- **テスト全件緑を確認**する
- 件数を plan に追記

### 9. テスター用 md（終点）

- 人間のテスト項目 md（テスター向け確認資料）を作成する。形式は SETUP-CHECKLIST B2 の選択に従う（既定: md ＋ スプレッドシート用 tsv）
- 含める要点: 背景・**今回入れた制限／変更の要約（付け間違い検知用）**・事前準備・参照系／更新系の画面操作表・スコープ外・改訂履歴
- tsv を併用する場合: UTF-8・タブ区切り・1 行目は固定ヘッダ・判定列は空欄（テスター記入用）。**正本は md** で、md を直したら tsv も直す
- 実装 plan md からリンクするのは tester md のみ。tsv への markdown リンクは置かない
- ユーザーが明示的に不要と言った場合のみ省略可。黙って省略して「完了」にしない

### 10. commit / push

- **人間手動**（SETUP-CHECKLIST B5）。指示があるまで `git commit` / `git push` しない
- push は新規 feature のみ。保護ブランチ禁止

---

## 禁止

- 手順 0〜9 の飛ばし・前後入れ替え（5 の条件付きスキップを除く）
- 既存処理変更なのに影響 golden 未生成のまま実装（5 の必須ケース）
- 5 のスキップを plan に理由なく行うこと
- desired の red 未確認のまま実装
- フィクスチャ投入後の全件確認なしで次へ進む
- テスター用 md なしで「タスク完了」とすること（ユーザーが明示的に不要と言った場合のみ例外）
- テストの裏付けなしに「動作を保証」「デグレなし」「問題なし」と書くこと
- 複数の修正をまとめて 1 回で検証すること（1 修正 = 1 検証）

---

## バグ挙動の扱い

- 仕様書がなく既存バグが多いコードでは、**バグ挙動は原則そのまま維持**し、golden として固定してよい。勝手に直さない
- バグ修正はビジネスロジック・仕様確認が必要なため、進行中の作業に混ぜず**別タスク**に切り分ける。要確認は SETUP-CHECKLIST B6 の起票先へ起票
- 同じ箇所の複数問題をまとめるときは、先に複合作業プラン（対象・順序・各修正の失敗予測）を plan md に書き承認を得る

---

## 例外（理由を明示しユーザー承認がある場合のみ）

- ドキュメントのみの変更 / テストコードのみの追加
- テスト基盤で覆えない対象（画面のないバッチ、外部連携、インフラ設定など）: 代替証拠を提示して承認を得る。黙って手順を飛ばすことは禁止
