# 作業ログ・タイムライン（自動同期骨子）

## 原則

- このファイルは**人間が手動で書かない**。AI が各ステップの完了時に追記・整合同期し続ける。
- 目的: AI が自走したステップ（因果関係）の歴史を、推測なしで一意に辿れる形で残す。後続のセッション・別の担当者が文脈を復元できるようにする。
- 形式は毎回同じ構造を保つ（`rules/00-governance-core.md` の「5. 文書トポロジーの固定」）。
- 証拠を書く。断定だけを書かない。

## スケルトン（複製して使う）

### タスクヘッダ

- タスク名:
- ブランチ:
- ベース SHA:
- 関連 plan md:
- 状態: 調査中 / 計画承認待ち / 実装中 / 検収待ち / 完了

### タイムライン

| 日時 | ステップ | やったこと | 証拠（コマンド・結果の要点・参照した md・ログの該当行） | 触ったファイル | 次に起きること（因果） |
|---|---|---|---|---|---|
| | | | | | |

### 因果チェーン（必要なときだけ）

- どのステップがどの問題を生み、どの修正につながったかを、参照つきで時系列に書く。

### 現在状態

- 今どのステップにいて、次のゲートは何か。

## 更新ルール

1. ステップが完了するたびに、タイムラインへ 1 行追記する（後からまとめて書かない）。
2. 手順が変わったら、plan md を先に直してから作業を続ける。ログへの追記はその後。
3. レスポンスを出す前に、このログへの反映が済んでいるかを確認する（`rules/02-response-self-check.md` のチェック項目 13）。
4. 記入は一意な参照（ファイルパス・見出し全文・コマンド）で行う。曖昧な略記をしない。

## 終点処理（検収完了後）

1. 人間の検収・テスト完了をヘッダの状態へ記す。
2. **確定した手順と結果を、該当 plan md へ反映する。** 細かい試行錯誤のログは plan md に残さない（必要なら退避先へ。退避先は gitignore された作業ログ用ディレクトリ。例: `work-logs/`）。
3. 結果や内容が変わった関連 md を更新する（`rules/01-workflow-gates.md` の「4. 検収後の md 反映（終点処理）」）。コード更新と md 更新はセット。
4. テスター用 md（人間のテスト項目）が必要な作業だった場合、作成済みかを確認する。
5. 再利用する可能性の低い完了済み成果物（テスター用 md 等）は `finished/` 配下（例: `finished/testing-plan/`）へ移動する。移動するときは、移動元を参照する全 md を検索し、関連 md の同期反映を必ず行う（一意な参照の維持作業の時間をケチらない）。
