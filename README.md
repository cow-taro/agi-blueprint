# agi-blueprint

**English guide: [en/README.md](en/README.md) ｜ 日本語ガイド: [ja/README.md](ja/README.md)**

汎用 AI 統治フレームワーク（初期テンプレート）。AI エージェントに「特殊な作業を確実に実行させるための規約」を、Ruby on Rails の conventions のように強固な既定値として与える。

`ja/`（日本語版）と `en/`（英語版）に**同一内容**の言語版を収める。

---

## このテンプレートの思想

1. **知識量から論理性へ** — モデルへの雑学の丸暗記は不要。長大コンテキストに生コードを丸ごと垂れ流す（無駄なフルスキャン）行為はコンテキスト追従性を悪化させ、ハルシネーション（錯覚）を誘発する。その問題を「劣化していない濃縮されたクレンジングデータ（Markdown）」を正本とし、一意な参照と証拠ベースの推論により決定論で AI の推論を統治するアプローチで解決する。
2. **Reasoning モデルの構造的合理性** — 思考（Thinking）の長考は、ルールの自己適用チェックという膨大なフィードバック、すなわち「深層の論理監査」の時間である。レスポンスの遅さを理由に確認プロセスを省略しない。
3. **厳格な参照規約の『結果』としての高キャッシュヒット** — 物理アドレス（行番号や `A-1` 等の曖昧な参照）を一切禁止し、リポジトリ全体で一意な「ファイル名」「見出し全文」「メソッド名」のみを主キー（インデックス）として指定させる。この厳格さの**結果**として文字列の配置（トポロジー）が固定され、高い確定キャッシュヒット率が随伴する。一般名詞の勝手な固有名詞的利用も厳禁とする。
4. **責任ある AI 利用** — AI は「錯覚する」「責任を取らない」ことを前提にプロセスを設計する。責任は人間が持ち、証拠ベースで計画させ、計画と実行を分離する。計画承認・検収という 2 つの承認ゲートに、レスポンス前の自己確認（AI 自身による品質チェック）とモード切替の適正化を組み込む。

## 構成

```
agi-blueprint/
├── README.md            — このファイル（日英併記の入口）
├── ja/                  — 日本語版（本ツリーの完全翻訳が en/ にもある）
│   ├── README.md        — 日本語版ガイド（構成・導入手順・拡張ルール）
│   ├── SETUP-CHECKLIST.md — 初期設定の棚卸し（必須入力／カスタマイズ／削除候補）
│   ├── rules/           — 常時ロード（毎回適用される高頻度規約のみ。4 件）
│   ├── skills/          — 随時ロード（稀にしか適用されない手順。9 件）
│   ├── templates/       — 記入式ひな形（5 件）
│   └── SAFE-AUTOMATION.md — 付録: 安全な AI 自動化の設計指針
├── en/                  — 英語版（ja/ と同一構成。SAFE-AUTOMATION.md を含む）
```

| 種別 | 読み込まれ方 | 収めるもの |
|---|---|---|
| rules | 常時（毎ターン適用） | 毎回適用される高頻度規約のみ |
| skills | 随時（該当作業のとき） | 稀にしか適用されない手順・ノウハウ |
| templates | 随時（複製して使う） | 記入式ひな形 |

**稀にしか適用されない内容を rules に置かない。** 常時コンテキストは最小限に保ち、注意力を守る。

## 採用手順（How to adopt）

1. `ja/` か `en/` の**どちらか一方**を選ぶ。両方を同じプロジェクトに入れない（参照が二重化して取り違えが起きる）。
2. 選んだツリーの中身を、利用するエージェントツールの規約置き場へ配置する（Roo / Claude 系なら `rules/` → rules ディレクトリ、`skills/` → skills ディレクトリ。規約機構がないツールなら `rules/` の内容をシステムプロンプトの先頭に固定する）。ツリーを分割して配置した場合は、ファイル間の相互参照を採用後の実パスへ読み替える（関連 md の同期反映）。
3. `SETUP-CHECKLIST.md` の A 章必須項目を埋める。対話で済ませたい場合は、AI に `skills/setup-wizard/SKILL.md` を読み込ませて実行する。
4. B 章を案件に合わせて調整し、C 章に該当する不要スキル・節を削除する。
5. `templates/project-premises-template.md` を複製し、プロジェクト固有前提の追記先として運用開始する。

## 言語選択について

英語版の方がトークン効率や追従性が高いという発想に基づく**英語限定はしない**。RAG で無関係なデータを投げ込むことに比べれば差は小さく、多くのモデルは日本語で指示しても内部 thinking は英語で動く。英語限定にすることで開発者がカスタマイズしにくくなることの方が問題である。言語は、開発チームが読んで直せる方を選ぶ。

## 運用中の拡張（繰り返す失敗の強制排除）

- 同じ失敗を 3 度したら、次のどちらかに昇格させる:
  - このプロジェクト固有の事情・罠 → 前提ファイルへ追記（`templates/project-premises-template.md` 由来）
  - 再利用できる汎用手順 → 新規スキルとして定型化
- 場当たり的に新しい番号付きルールファイルを作らない。

## 推奨環境（2026-10-15 補足）

- **IDE: Roo Code または Zoo Code を推奨する。**
- **LLM: GLM 5.3 flash と GLM 5.3 を推奨する。**


## 保守ルール

- 再利用する可能性の低い完了済み作業は `finished/` フォルダへ保存する。
- テスト完了後、テスター用 md 等のテスト資料を `finished/testing-plan/` のようなフォルダへ移動するときは、関連 md の同期反映を必ず行う。
- md のリファクタなどでファイルを移動するときは、一意な参照の維持作業の時間をケチらない。移動元を参照する全 md を検索して同期反映する。
